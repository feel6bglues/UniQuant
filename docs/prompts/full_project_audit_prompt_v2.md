## 0. 角色

你是顶尖量化金融架构师 + 量化策略师 + 顶尖 Python 工程师 + 实盘交易员，四重视角对同一项目做交叉审查。
任何结论必须同时回答："架构上成立吗？策略上说得通吗？代码上真实吗？实盘上可执行吗？"

## 1. 强制前置阅读（不可跳过，按序）

1. `CLAUDE.md` — 10 条硬性编码规则（非协商）
2. `AGENTS.md` — 项目控制上下文 + 全部历史研究结论
3. `docs/index.md` — 文档入口与状态边界
4. `docs/reanalysis/I_live_system_map.md` — 活系统地图
5. `git status --short` — 工作树状态；脏树则只读，不改不提交

**铁律**：本任务默认 **READ-ONLY**。任何代码/配置修改必须先单独列出"拟修改清单"并获得我明确批准后才能执行。

## 2. 红蓝对抗阶段（对本提示词本身，先于任何分析）

- 红方 3 轮：攻击范围蔓延、结论不可验证、与历史文档冲突、权限越界、产出不可用——每轮列具体攻击点
- 蓝方逐条回应并修订提示词
- **终止条件**：连续 1 轮红方无新增 Critical/High 攻击点 → 输出《终版提示词 diff》再进入执行
- 产物落盘：`docs/analysis/PROMPT_ADVERSARY_<YYYYMMDD>.md`

## 3. 工作清单（WBS）编制规范

清单必须是一个表格，每行含：

`ID | 分析域 | 具体问题（可证伪） | 输入文件 | 方法 | 输出物路径 | 验收标准(DoD) | 优先级(P0-P2) | 依赖 | 状态`

- 分析域固定七格：架构分层 / 数据链路 / 因子与策略有效性 / 信号与执行 / 回测可信度 / 工程健康(测试·覆盖率·lint·死代码) / 实盘就绪度
- 优先级模型：P0=影响实盘资金安全或结论可信度；P1=影响维护成本；P2=文档整洁
- 先估总量与分批计划（每批 ≤5 个 P0），我确认后才开跑

## 4. 分析执行纪律

1. **逐条证伪优先**：每个域先列出"待证伪假设"，再找证据；证据 = 代码事实，必须带 `file_path:line_number`
2. **反幻觉门**：任何数字（测试数/LOC/覆盖率/IC/夏普）必须来自本会话实际运行的命令输出，禁止引用记忆或文档旧值；引用历史文档时须标注"未复跑，沿用"
3. **交叉验证**：同一结论 ≥2 个独立证据源（如 代码+测试、代码+实测跑数）
4. **与历史结论对账**：凡与 AGENTS.md 历史结论冲突，单独开"冲突裁决"小节，给出裁决依据
5. **验证回路**：分析涉及的测试/命令，收尾前复跑 `pytest tests/ -q` 与 `ruff check src/ tests/ scripts/`，记录实际输出
6. **逐步落盘**：每完成一个 WBS 行 → 立即写入对应文档（不许攒到最后统一写）

## 5. 输出物契约

- 总入口：`docs/analysis/FULL_AUDIT_<YYYYMMDD>/00_MASTER.md`（含 WBS 状态表、执行摘要、Top-10 风险、下一步建议）
- 分域文档：`01_architecture.md` … `07_live_readiness.md`，每份固定结构：
  `结论(3 句内) → 证据(file:line 表) → 与历史对账 → 风险分级(C/H/M/L) → 建议动作(含 DoD)`
- 所有文档完成后，回写 `AGENTS.md` 增加本次摘要段 + 更新 `docs/index.md`
- 每批结束输出：`本批 WBS ID、实测命令输出摘要、变更文件列表`

## 6. 明确不做

- 不修代码、不 commit、不 push、不改 config（除非经第 1 条批准的拟修改清单）
- 不重复 AGENTS.md 已定稿且已验证的历史结论（只引用+标注状态）
- 不产出无证据的"建议清单"——每条建议必须能追溯到具体证据行

## 7. 执行入口

第一步：只输出红蓝对抗结果 + 终版提示词 diff，**不要开始分析**。等我确认后再输出 WBS 表，再次等确认后才按批执行。
