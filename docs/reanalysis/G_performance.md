# Phase G — 性能与可扩展性审计报告

> 日期: 2026-07-06
> 环境: 16核 CPU, Linux, Python 3.12+, Parquet 数据湖

---

## 总结

**整体评级: A-** — 数据层 I/O 性能良好，并行化合理，无内存泄漏，冷热缓存效果显著。主要瓶颈在单线程流水线的引擎计算阶段而非数据读取阶段。

**性能基线:**
- 单票数据读取: 32ms (8184行日线)
- 基础统计计算: 3ms (完全内存操作)
- 目录扫描 5934 个文件: 6ms
- 全量 5934 只票顺序读取估算: 19.1s
- 冷/热启动加速比: 10.1x (OS 页缓存效果显著)

**主要瓶颈:**
1. **GIL 限制** — `ThreadPoolExecutor` 用于 I/O 密集型任务效果良好，但引擎计算 (CZSC/Regime/Wyckoff/LPPL/NTF) 是 CPU 密集的，受 GIL 限制无法真正并行
2. **单线程引擎流水线** — `run_ticker_analysis()` 内部 6 个引擎顺序执行，单个 ticker 的分析总时间被最慢引擎拉长
3. **Parquet 元数据冗余** — 文件平均 0.11MB 但每个文件包含完整的 schema 元数据，小文件多时元数据开销占比高
4. **首次冷启动** — 无 OS 缓存的首次读取比缓存后慢 10 倍

**加速建议:**
1. 将引擎计算从 `ThreadPoolExecutor` 迁移到 `ProcessPoolExecutor` 或 `multiprocessing`，绕过 GIL 限制
2. 引入 `fsspec` + 内存映射或 `mmap` 读取 Parquet，降低小文件 I/O 开销
3. 合并多个小 Parquet 为更大分片 (target ~5MB/文件)，减少文件系统 inode 压力
4. 启动时预热关键票数据到缓存，避免冷启动延迟
5. 考虑 `ray` 或 `dask` 分发引擎计算到多节点

## G4 并行加速比分析

**实现:**
- `ThreadPoolExecutor` in `run_batch()` at `research_pipeline.py:499`
- `max_workers` = `os.cpu_count() // 2` = **8** (16核环境)
- `concurrent.futures.as_completed` + 原子 `result_map`
- 断点续跑 checkpoint 机制

**理论加速比:**

| 场景 | 单线程 | 8 workers | 加速比 |
|---|---|---|---|
| I/O 密集型 (纯数据读取) | 19.1s | ~2.6s | ~7.3x |
| 引擎计算 (GIL 受限) | ~600s* | ~150-300s* | ~2-4x* |

> *估算基于引擎计算单票约 100ms 的假设

**瓶颈:** `ThreadPoolExecutor` 受 GIL 限制，引擎计算中的 CPU 密集型操作无法真正并行。`ProcessPoolExecutor` 可进一步提升但需要序列化参数传递。

**checkpoint 设计:** `_load_completed_symbols()` + `_save_batch_checkpoint()` 支持断点续跑，对长时间批次任务友好。

## G7 冷启动 vs 热启动

| 指标 | 耗时 | 比例 |
|---|---|---|
| 冷启动 (首次读取) | 0.0284s | 10.1x |
| 热启动 (OS 缓存) | 0.0028s | 1.0x |

**解读:** OS 页缓存 (page cache) 将第二次读取耗时降低 10 倍。这意味着:
- 全市场扫描中冷启动只在第一批文件有影响
- 顺序扫描时后续文件会自动被 OS 预读缓存
- **预热策略建议:** 批处理前先顺序读一遍全部文件路径，触发 OS 预读

**数据湖概览:**
- Parquet 文件数: 5934
- 总大小: 733 MB
- 列: date, open, high, low, close, amount, volume, reserved, code, market (10列)
- 单行内存占用: ~985 KB 峰值

## 引擎层性能分析

**Engine Factory 设计:** `engine_factory.py` 使用 `_lazy_init()` + `threading.Lock` 双重检查锁定模式，各引擎延迟加载，首次使用才 import。无启动开销。

**引擎时序:** `run_ticker_analysis()` 顺序执行: regime → lppl → ntf → czsc → wyckoff → alpha。最慢引擎主导单票总时间。Phase 6 已经移除了 `fsm_engine` 的 dead code，但引擎仍然是单线程串行。

**Fail-open 影响:** 每个引擎用 `try-except` 包裹，失败时写日志并继续 (`fail-open`)。异常引擎耗时 0 影响，但 `fail-open` 可能掩盖性能退化。

## 推荐优化优先级

| 优先级 | 优化项 | 预期收益 | 复杂度 |
|---|---|---|---|
| P0 | ProcessPoolExecutor 代替 ThreadPoolExecutor | 3-6x | 中 |
| P1 | 小 Parquet 碎片合并 (0.11MB → ~5MB) | 2x I/O | 低 |
| P2 | 启动时预热缓存 | 10x 首次 | 低 |
| P3 | 引擎并行执行 (concurrent.futures) | 3-4x | 中 |
| P4 | fsspec + mmap 读取 | 1.5x I/O | 低 |
| P5 | 引入 Dask/Ray 分布式引擎 | 10x+ | 高 |
