## C2 停复牌处理

### 代码位置

- `unified_engine.py:228-251` — 停牌拦截（防线 C）
- `unified_engine.py:248-251` — `volume=0` 停牌拒绝
- `unified_matching_engine.py:57` — `is_trading_day()` 交易日检查
- `unified_matching_engine.py:226-227` — T+1 买/卖交易日检查

### 机制分析

```
┌─ unified_engine.py run() 主循环 ──────────────────────────┐
│  1. is_trading_day() → 非交易日跳过                      │
│  2. 挂单处理 → vol <= 0 → 停牌拒绝, clear pending_order │
│  3. 防线 A: T+1 检查 (buy_date → sell_date)             │
│  4. 防线 C: volume=0 停牌拦截 (execute 前)              │
└──────────────────────────────────────────────────────────┘
```

**优点**:
1. 非交易日先跳过（`is_trading_day`），使用收盘价更新权益
2. vol<=0 时清除挂单，不产生虚假成交
3. T+1 和停牌两套防线**独立运作**，互不干扰

**问题**:
1. 停牌判断仅依赖 `volume=0`，未校验复牌首日的涨跌停限制
2. 复牌首日未设置特别的涨跌停保护（复牌首日涨跌停限制与正常日不同）
3. `unified_matching_engine.py:57` 的交易日过滤被 T+1 逻辑覆盖，但停牌交易日挂单未处理

**风险评估**: 低 — 停牌处理基本正确。volume=0 拦截可覆盖绝大多数停牌场景（成交量=0 时自然停牌），但真实 A 股存在少数"无量涨停"仍有少量成交，此场景可能被误判为停牌。

## C3 复权链一致性

### 实现文件

`src/uniquant/data/pipeline/data_adjuster.py` (308 行)

### 算法核心

```python
# MergeAsOf 匹配因子 → 向量化计算
df_merged = pd.merge_asof(
    df_raw.sort_values("date"),
    df_factor.sort_values("date"),
    on="date", direction="backward"
)
df_merged["factor"] = df_merged["factor"].ffill().fillna(1.0)

# HFQ: Price * Factor
# QFQ: Price * Factor / LatestFactor
```

`data/fq/` 目录**不存在**，`gbbq.parquet` 文件也不在标准位置。复权因子通过 `FactorManager` 从通达信本地数据计算并保存。

| 检查项 | 结果 |

## C7 数据缓存一致性

### 缓存架构

```
┌─ CacheCoordinator ───────────────────────────────────┐
│  CacheFactory.create("disk", cache_dir)              │
│  ├─ DiskCacheBackend (持久化, data/cache/)           │
│  └─ MemoryCacheBackend (运行时, 默认 100项)          │
├─ generate_cache_key(prefix, *args, namespace)        │
│  → "{namespace}:{prefix}:{arg1}_{arg2}"             │
├─ set(key, value, ttl, data_type)                    │
└─ check_consistency(symbol, cached, source)           │
└──────────────────────────────────────────────────────┘

┌─ MarketLevelCache (线程安全) ─────────────────────────┐
│  threading.Lock 保护所有读写                           │
│  Regime/NTF/Benchmark 全市场共享缓存                  │
│  _today() 日期校验 → 过期自动失效                     │
└──────────────────────────────────────────────────────┘
```

### 缓存 Key 设计

```python
# 格式
"{namespace}:{prefix}:safe_arg1_safe_arg2"
# 示例
"default:data:000001_SZ_2024-01-01_2024-12-31"
```

### TTL 配置

| 数据类型 | TTL | 配置来源 |
|---|---|---|
| Stock | 3600s (1h) | DataServiceConstants.CACHE_TTL_STOCK |
| Index | 3600s (1h) | DataServiceConstants.CACHE_TTL_INDEX |
| ETF | 3600s (1h) | DataServiceConstants.CACHE_TTL_ETF |
| Realtime | 60s (1m) | DataServiceConstants.CACHE_TTL_REALTIME |
| Industry | 86400s (1d) | DataServiceConstants.CACHE_TTL_INDUSTRY |
| General | 3600s (1h) | DataServiceConstants.CACHE_TTL_GENERAL |

### TTL 别名问题

`src/uniquant/shared/constants/data.py:133-139` 中 TTL 常量被定义为 `_CacheTTLAlias` 类型，而非实际整数值。实际值在 `:185-187` 定义。

```python
# 别名 (Line 133)
CACHE_TTL_STOCK = _CacheTTLAlias("CACHE_TTL_STOCK")
# 实际值 (Line 185)
CACHE_TTL_STOCK = 3600
```

**潜在问题**: 别名定义先出现，实际值在后，若某些模块在解析时使用了错误的引用点（别名而非实际值），可能导致 TTL 失效。

### 多进程竞态风险

| 级别 | 保护 | 风险 |
|---|---|---|
| MarketLevelCache | threading.Lock | ✅ 进程内安全 |
| DiskCacheBackend | 无 IPC 锁 | ❌ 多进程覆盖风险 |
| CacheCoordinator.get/set | 无分布式锁 | ❌ 多进程写冲突 |

**影响**: 当多个进程（如 batch 批处理）同时读写磁盘缓存时，可能发生数据损坏或过期覆盖。目前无明显分布式缓存需求（单进程容器化部署可规避）。

### 缓存一致性问题

`CacheCoordinator.check_consistency()` 仅比较最新日期的 `cached >= source`，未校验数据内容的逐行一致性。

**风险评估**: 中。TTL 别名歧义和多进程写竞争是潜在问题，但当前部署模式（单进程）可规避后者。
