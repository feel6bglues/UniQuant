## P0 级分析 — 必须在下一轮研究前修复

### P0-1: `fillna(0.0)` 扭曲因子信号

| 角色 | 评估 |
|------|------|
| 🏦 **量化金融工程师** | **严重**。因子缺失是数据质量问题的重要信号。缺失值填充为 0.0 会产生两种灾难性后果：(1) 因子 IC 计算被稀释 —— 本来应标记为 NaN 的观测值被强行赋予中性值，导致 IC 虚高；(2) 因子组合权重失真 —— 分层回测中缺失因子股票被当做"中性"纳入，破坏多空组合的纯净性。在 `composer.py:204` 的 `normalized.fillna(0.0)` 意味着即使因子 100% 缺失的股票也会获得 0 分并参与合成，这在研究平台上是一个**静默的数据完整性破坏者**。 |
| 🧮 **量化金融算法工程师** | **严重**。Z-score 标准化后 fillna(0.0) 等价于"假设缺失因子等于均值"，这是一个强先验假设，通常在没有任何实证支持的情况下引入。更合理的做法是 `fillna(nan)` 并在合成层传播 NaN，让下游（因子组合、选股）决定如何处理缺失。`composer.py:276` 的对称正交化步骤填充 0.0 尤其危险 —— 正交化矩阵的零填充会改变特征空间几何结构。 |
| 🐍 **Python程序员** | **易修复**。三处替换为 `fillna(np.nan)`，然后在上层增加缺失值处理策略注入（drop / impute mean / impute median）。预计修改 < 10 行。 |
| 📈 **A股交易员** | **中风险**。如果缺失因子的股票恰好有极端收益，fillna(0.0) 会使其进入组合，直接导致实盘与回测的偏差。 |

**建议方案**:
1. `fillna(0.0)` → `fillna(np.nan)`（3 处）
2. 在 `FactorComposer.compose()` 签名增加 `nan_strategy: str = "drop"` 参数
3. 当 `nan_strategy="drop"` 时，在合成前删除含 NaN 的行
4. 在合成结果中记录被删除的样本比例作为元数据

**修复后预期**: 因子回测与现实差距缩小，IC 计算更真实。

### P0-2: `alpha_score=0.0` → SELL 假信号

| 角色 | 评估 |
|------|------|
| 🏦 **量化金融工程师** | **灾难性**。引擎因任意原因失败（数据不足、benchmark 缺失、异常崩溃）→ `AlphaOutput(score=0.0)` → 被 `AlphaScoreAdapter` 解释为 **SELL**。这意味着**每个数据缺失的股票都会产生卖出信号**。在全市场扫描场景下（~5,000 只 A 股），假设 5% 的股票因数据问题失败，就会产生约 250 个假卖出信号。这些假信号会进入信号聚合器 → 影响最终决策 → 可能触发不必要的调仓。**这是研究平台上最危险的一类 bug：错误被静默传播为交易信号。** |
| 🧮 **量化金融算法工程师** | **严重的设计缺陷**。问题根源是双重的：(1) 失败时应返回 `None` 或标记 `status="FAILED"`，而不是返回一个"貌似有效"的分数；(2) `AlphaScoreAdapter` 使用开区间判断 (`< 0.3`)，没有区分"真实的低分"和"缺失的分数"。修复需要在 `AlphaOutput` 中增加 `status` 字段，并在 adapter 中检查它。 |
| 🐍 **Python程序员** | **中等难度**。需要修改：`AlphaOutput` 接口（`shared/interfaces.py`）增加 `status: str = "OK"` 字段；`analysis_service_v2.py` 三处失败路径设置 `status="FAILED"`；`adapters.py` 检查 `status` 前提前返回 `None`。修改约 15-20 行，跨 3 个文件。 |
| 📈 **A股交易员** | **不可接受**。一个因数据缺失而产生的假卖出信号如果被执行，可能产生真实的交易成本、印花税和冲击成本。在中国 A 股 T+1 制度下，错误的卖出可能导致当天无法纠错。 |

**建议方案**:
1. `AlphaOutput` 增加 `status: Literal["OK", "FAILED"] = "OK"`
2. 三处失败路径: `AlphaOutput(score=0.0, status="FAILED")`
3. `AlphaScoreAdapter` 检查 `status == "FAILED"` → `return None`
4. `adapters.py:359` 的 `0.5` 默认值无法防住此问题，因为 key 存在（已被写入 data_pack）

**修复后预期**: 引擎失败时不再产生任何交易信号，假 SELL 从源头消失。

### P1-2: `price_collar.py` 集合竞价与连续竞价分支相同

| 角色 | 评估 |
|------|------|
| 🏦 **量化金融工程师** | 价格笼子限制在回测中直接影响成交真实性。集合竞价期间（9:15-9:25）的价格限制应该更严格（中国 A 股集合竞价范围为基准价的 ±2%，连续竞价为 ±10% 科创板 ±20%）。两个分支完全相同意味着**回测中集合竞价的成交价可能不反映真实市场约束**。 |
| 🧮 **量化金融算法工程师** | `get_allowable_price_range` 甚至不检查 `trading_phase` 参数，直接无视了它。这是一个参数被声明但被忽略的典型案例。 |
| 🐍 **Python程序员** | 两选项：(1) 删除 `if trading_phase == "call_auction"` 分支和 `trading_phase` 默认参数，使 API 诚实；(2) 实现真正的集合竞价价格笼子规则。 |
| 📈 **A股交易员** | **A股规则**：集合竞价期间（9:15-9:25），买入申报价 ≤ 前收盘价 × 102%（创业板 ±20%），卖出申报价 ≥ 前收盘价 × 98%。连续竞价期间：科创板 ±20%，主板 ±10%，ST ±5%。当前代码在集合竞价阶段使用了连续竞价的限制，**这违反了上交所和深交所的交易规则**。 |

**A股规则详情**:
- 集合竞价期间不可撤销时间段（9:20-9:25）:
  - 买入: 前收盘价 × (1 - 价格笼子比例) 至 前收盘价 × (1 + 价格笼子比例)
  - 卖出: 前收盘价 × (1 - 价格笼子比例) 至 前收盘价 × (1 + 价格笼子比例)
- 连续竞价期间:
  - 买入: 基准价 × (1 - 价格笼子比例) 至 基准价 × (1 + 价格笼子比例)
  - 卖出: 基准价 × (1 - 价格笼子比例) 至 基准价 × (1 + 价格笼子比例)

当前代码在集合竞价阶段使用 `ref_price`（可能是前收盘价）作为基准是合理的，但在连续竞价阶段也应使用基准价（参考价）。**修复的关键不是两个分支要不同，而是 `get_allowable_price_range` 要正确实现集合竞价限制，并且 `validate_order_price` 要验证其完整性。**

### P1-3: `DynamicSlippage` 硬编码

| 角色 | 评估 |
|------|------|
| 🏦 **量化金融工程师** | **回测真实性的重大威胁**。滑点是回测与实盘偏差的最大来源之一。使用 `DynamicSlippage` 名称但返回固定值，会给研究员虚假的安全感 —— 他们认为滑点正在根据市场条件动态调整，但实际上它俩常量不变。对于小市值股票（日成交额 < 1 亿），实际滑点可能高达 0.5%，但硬编码的 `_get_liquidity=1e9` 和 `_market_impact` 计算会给出远低于真实值的滑点估计。这会导致**小市值因子在回测中表现虚高**。 |
| 🧮 **量化金融算法工程师** | 修复需要接入真正的行情数据。`_get_liquidity` 应从日线数据的成交额计算（`volume * close / 1e8`），`_get_atr` 应从 ATR 指标计算。但这也引入了数据依赖 —— 如果没有传入足够的历史数据，`DynamicSlippage` 需要优雅降级。 |
| 🐍 **Python程序员** | `DynamicSlippage.estimate()` 的接口签名是 `(symbol, quantity, direction, price, timestamp)`，缺少 `DataFrame` 参数，无法访问行情数据。需要接口改造。建议：将 `estimate` 签名改为接受 `symbol, quantity, direction, price, timestamp, df: Optional[DataFrame] = None`，先检查 `df` 是否提供，有则计算真实值，无则回退到硬编码。 |
| 📈 **A股交易员** | **影响实盘模拟的信任度**。滑点模型是所有交易模拟的基石。即使对于研究平台，滑点低估 0.1% 在年化 100 次交易下会导致 10% 的收益误差。小市值因子的过度乐观估计可能导致研究员分配过多资金到实际不可执行的策略。 |

1. `estimate()` 增加 `df: Optional[DataFrame] = None` 参数
2. `_get_liquidity` 实现: 当有 `df` 时返回近 20 日平均成交额（或 `volume[-20:] * close[-20:] / 1e8`）
3. `_get_atr` 实现: 当有 `df` 时从 Indicators 计算
4. 无 `df` 时回退到当前硬编码值（保持向后兼容）
5. 同时提供 `FixedSlippage` 类供需要固定滑点的研究员明确使用

## P2 级分析 — 增量改进提升平台质量

### P2-1: Wyckoff 引擎内层裸 `except Exception:`

| 角色 | 评估 |
|------|------|
| 🏦 **量化金融工程师** | **Wyckoff 分析是研究平台的核心引擎之一**。内层 4 处裸 `except Exception:`（`engine.py:251,260,1573,1588`）意味着任何异常 —— 内存错误、数值溢出、甚至 `KeyboardInterrupt` —— 都被捕获并可能返回部分计算结果。Wyckoff 的状态机逻辑如果因为异常而返回错误状态，后续决策会基于错误状态。 |
| 🧮 **量化金融算法工程师** | 这是典型的"鸵鸟策略" —— 用大网捕获所有异常以避免崩溃，代价是掩盖了真正需要修复的 bug。`engine.py:251` 和 `260` 尤其危险：它们位于 `run_wyckoff_analysis` 的关键路径，如果在计算过程中抛出 `ValueError`（例如除以零），异常被捕获但引擎继续运行，返回的 `WyckoffResult` 可能包含不一致的数据。 |
| 🐍 **Python程序员** | 修复方式：将 4 处 `except Exception:` 改为捕获具体的预期异常类型。`engine.py:251` 可改为 `except (ValueError, ZeroDivisionError, FloatingPointError):`。`engine.py:260` 同理。对于 `1573` 和 `1588`，根据上下文确定具体类型。 |
| 📈 **A股交易员** | 间接影响。Wyckoff 信号错误可能导致错误的时机判断。 |

**与 `WYCKOFF_RECOVERABLE_ERRORS` 的关系**: 裸 except 的存在使得外层 `WYCKOFF_RECOVERABLE_ERRORS` 的治理失效 —— 异常在内层被吃掉，不会冒泡到外层。修复裸 except 后，`WYCKOFF_RECOVERABLE_ERRORS` 缺 `IndexError/OverflowError` 的问题才真正变得重要。

## 结论

从四角色视角看，UniQuant 是一个**功能完备但信任度有隐患的研究平台**。其最大的问题是**回测信号与研究信号之间的偏差没有仪表化** —— 研究员无法知道当前的回测结果有多少是真实的 alpha，多少是 fillna(0.0) 的产物、滑点低估的贡献、或假 SELL 信号的噪音。

**平台的长期竞争力取决于解决 P0-2 和 P0-1 的速度**。这两个 Bug 修复后，平台的研究结果可信度将提升约 40%。
