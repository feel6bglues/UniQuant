## 二、最严重发现：汇总层存在虚构代码证据（已坐实）

这是唯一"硬失实"的代码内容引用，**由架构师与事实核查员两方独立确认**。

`09_cross_module_integration.md` 与综合报告为**最高优先级 P1 结论（LPPL SELL 优先级遗留）**贴出了一段"精确到行号"的代码：

```python
# 报告声称 arbitrator.py:32-42 内容
ENGINE_PRIORITY = {LPPL:1(最高), CZSC:2, ..., QAR:9}
# 报告声称 unified_engine.py:337-348
if engine == "LPPL" and direction == "SELL": priority = 0
```

**代码库实际**（`signal/arbitrator.py:32-42`，核查员实测）：键为小写、`lppl:99`（**最低**优先级）、`fsm:1`（最高）。LPPL 优先级方向**完全颠倒**；`unified_engine.py:337-348` 实为 `pending_order` 结转逻辑，全仓无 `ENGINE_PRIORITY`、无 `priority` 变量。

**三重加重情节**：
1. 报告自我标榜"代码引用精度：所有引用精确到行号"——在最关键处提供了虚构代码，直接推翻该自我背书；
2. 该虚构结论被综合报告继承为"整体优秀、P1 立即修复"的**地基**；
3. 报告 09 的"LPPL 最高优先级"与**报告 03 自己的结论**（LPPL 零预测力、`diagnostic_only=True`）自相矛盾——同一批报告内部打架。

> ⚠️ **重要保留**：该问题背后的**行为担忧是真实的**——`unified_engine.py:337-348` 实际代码确实通过 `sig.reason` 含 "lppl" 单独拦截 LPPL SELL 建挂单、绕过统一仲裁路径。即"LPPL SELL 在回测引擎中被特殊处理、可能与统一仲裁不一致"这一发现方向成立，但报告是用**假代码**支撑了一个**未被准确定位**的问题。必须在真实代码上重新定位后重述。

## 七、给决策者的底线

**值得肯定的资产（专家团共识）**：

**必须警惕的**：汇总层（09/综合）的可信度构建方式有硬伤——**混入虚构代码、聚合数字错、自我循环背书**。当一个评审声称"整体优秀/0 HIGH"，却在自己发现的问题定级上反复漂移、甚至用假代码支撑最高优先级结论，这种内部不一致本身就是可信度红旗。

**落地实盘前必须先做的三件事**：
1. **重做报告 09 的 LPPL 结论**：在真实 `arbitrator.py`/`unified_engine.py` 上用真实代码重述（实际存在 lppl reason 特判，但机制与报告描述完全不同）。

3. **闭合端到端风控链路**：确认"信号 → sizer（满仓/fail-open）→ 合规引擎（是否在主链路）→ UI（mock 回落）"一笔交易从信号到下单/展示是否真的闭合——各报告各审一段，没人串起来验证过。
